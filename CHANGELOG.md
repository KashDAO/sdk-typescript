# Changelog

All notable changes to `@kashdao/sdk` will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

While the package is `0.x`, minor versions may include breaking changes —
breaking changes are explicitly called out in the entry.

## [Unreleased]

## [0.4.0] — 2026-11-12

Everything a partner integrating the partner public API v1 needs: its REST
surface, the `account` option for acting for one of its users, the partner
webhooks, typed problem codes, and response parsing that keeps working when
the API adds a field or a value.

### Breaking (API diff against 0.3.2)

Generated by `scripts/api-diff.ts` against the published 0.3.2: every
export whose public type changed is listed once, under the reason it
changed, including Zod schemas whose schema object changed while what they
parse did not (`--check-changelog` holds this list to the script's output).
The schemas are the only exports removed from the root entry, and each is
still exported from `@kashdao/sdk/schemas`. Entries marked additive do not
break code that only calls them.

### Validation changes (schema corpus against 0.3.2)

The type-level list above cannot see what a schema accepts at runtime.
`scripts/api-diff.ts` therefore also runs a fixed corpus of inputs through
every schema exported by both 0.3.2 and this release (28,996 inputs across
57 schemas) and lists every schema where the two disagree;
`--check-changelog` holds this list to its output. Every difference found
falls into one of three classes:

- **Open value sets accept any string.** A status, side, kind, reason or
  resolution field (and the enum schemas `MarketStatusSchema`,
  `TradeStatusSchema`, `RedemptionKindSchema`, `MarketResolutionStateSchema`
  and `MarketNotTradeableReasonSchema` themselves) accepts a value 0.3.2
  rejected. Described under Changed, with the migration.
- **Integers must be safe integers.** Under zod 4, an integer field (a
  count, an index, a chain id, a limit) rejects a number above
  `Number.MAX_SAFE_INTEGER` (2^53 - 1), which 0.3.2 accepted. No such value
  is sent by the API, and JavaScript cannot represent one exactly.
- **Two trace schemas strip unknown keys.** `TraceEventDataSchema` and
  `TraceRetentionSchema` were strict in 0.3.2 and failed a whole
  `traces.get()` response on a field the server added; they now drop it, as
  every other response schema does (described under Changed).

The corpus is a sample, not a proof, and neither check sees defaults the
client applies, retry behaviour or error classification: those changes are
described under Changed.

### Added

- **Partner accounts.** `kash.partnerAccounts` (`PartnerAccountsClient`)
  wraps `/v1/partner/accounts` for partner keys with the `partner:accounts`
  scope: `create`, `get`, `findByExternalId` (the account, or `null`),
  `list` (a `Page`), `update` (destination and/or country), `suspend`,
  `reactivate`, `release` and `waitUntilActive` (polls until active;
  rejects with `ACCOUNT_NOT_ACTIVE` on `provisioning_failed`, `released` or
  `suspended`, and on timeout). `create` returns
  `{ account, outcome, idempotentReplay }`.
- **One result shape for both partner creates** (`PartnerCreateResult`,
  `PartnerCreateFacts`, `PartnerWriteOutcome`): the resource under its own
  key, `outcome` (`'created'` when this request created it, `'existing'`
  when it already existed and was returned) and `idempotentReplay` (`true`
  exactly when the server replayed its stored response for the
  `Idempotency-Key`). The resource is nested so a field the API adds can
  never collide with these.
- **Partner withdrawals.** `kash.partnerAccounts.withdrawals`
  (`PartnerWithdrawalsClient`): `quote`, `create`, `get`, `list` and
  `waitForCompletion` (polls until `completed`, `failed` or `cancelled`).
  `create` requires an `idempotencyKey`, in its type and at runtime, so a
  retry can never withdraw twice, and returns
  `{ withdrawal, outcome, idempotentReplay }`. Partner `list` limits are
  checked (1 to 100) before sending.
- **Balance.** `kash.balance.get()` (`BalanceClient`) returns the acting
  account's on-chain USDC, the amount held by pending withdrawals and what
  is available, as integer strings in USDC atomic units.
- **The `account` option** (`AccountRequestOverrides`), sent as the
  `Kash-Account` header, on every method whose route accepts it: `balance`,
  `trades` (including `waitForCompletion`), `portfolio` (including
  `watchPositions`), `redemptions` and `traces`. Markets, quotes, webhooks,
  account usage and the partner routes do not take it, so sending the
  header where the API answers `400 ACCOUNT_HEADER_NOT_ALLOWED` does not
  compile. It is checked as a UUID before sending, and the conditional-GET
  cache keeps a separate entry per account.
- **Typed problem codes.** `KASH_ERROR_CODE` names the codes a partner
  branches on (`ACCOUNT_NOT_ACTIVE`, `INSUFFICIENT_BALANCE`,
  `WITHDRAWAL_BELOW_MINIMUM`, `WITHDRAWALS_HELD`,
  `DESTINATION_NOT_SUPPORTED`, `RELEASE_REQUIRES_EMPTY_ACCOUNT`,
  `ACCOUNT_HEADER_NOT_ALLOWED`, `IDEMPOTENCY_REQUEST_IN_PROGRESS`,
  `IP_NOT_ALLOWED`, the idempotency-key format codes and others), and
  `KashError.code` is typed `KashErrorCode`: those codes plus any string.
- **`retryAfterSeconds` on every `KashError`**: the server's `Retry-After`
  in seconds when it sent one, `undefined` otherwise, so one read covers a
  rate limit, an outage and a hold (`WITHDRAWALS_HELD`, the time left on
  the 24-hour hold). The subclass fields read the same value; `toJSON`
  includes it.
- **Unknown webhook types no longer throw** (a type-level break for 0.3.x
  handlers: see Breaking). After the signature and the
  envelope check, a delivery whose `type` this SDK version does not know
  is returned as an `UnknownWebhookEvent`
  (`{ known: false, id, type, apiVersion, createdAt, data: unknown }`).
  Recognise it with `isUnknownWebhookEvent` and handle unknown types in a
  default branch; past that check `event.type` narrows over the known
  types. A known type that does not match its schema is still refused.
  `constructEvent` now returns `ConstructedWebhookEvent`
  (`WebhookEvent | UnknownWebhookEvent`).
- **In-progress idempotent requests are retried.** A keyed request that
  times out on the client and meets `409 IDEMPOTENCY_REQUEST_IN_PROGRESS`
  on the retry (the server still running the first attempt) is retried
  with the same key inside the normal retry budget, honouring the API's
  `Retry-After`. It never sends such a retry 45 seconds or more after the
  call's first send: the API holds its claim on the key for 60 seconds and
  then lets a new request take it over and run again, so the SDK stops
  15 seconds short. When the conflict reaches the caller, read the
  resource's state before retrying with the same key. The retry hook reports
  `reason: 'idempotency_in_progress'`. A request without a key is never
  retried on it.
- **`trades.create` sends a `clientRequestId` by default.** When the body
  has none, the SDK generates one per call and sends the same one on every
  retry of that call; a `clientRequestId` you pass always wins. Why: the
  `Idempotency-Key` claim lasts 60 seconds, is skipped when the API cannot
  record it, and is released by any error response (including the 503 sent
  when a trade was recorded but its event pipeline was down), and a retry
  after any of those ran the trade route again and could record a second
  trade. The API checks `clientRequestId` against a unique (account,
  clientRequestId) in the database with no time limit, so a repeat of the
  call now returns the trade already recorded (`idempotent: true`). A `409
CLIENT_REQUEST_ID_CONFLICT` on a generated id (a concurrent attempt of the
  same call recorded the trade) is sent once more and returns that trade.
  Visible change: the request body, and `trade.clientRequestId` on
  trades created without one (was `null`, now the generated id). There is
  no opt-out, because no caller is served by one: the id is used only by the
  retries of the call that generated it, and two calls never share one. To
  retry a trade yourself across calls, pass the failed call's
  `err.clientRequestId` (every error `trades.create` throws carries the id
  it sent, as the new optional `KashError.clientRequestId`), or your own
  id. `idempotent: true` on the result can now come from the call's own
  retry, when an earlier attempt recorded the trade and its response was
  lost.
- Two entry points. `@kashdao/sdk/partner` holds the types of the partner
  surface: every new resource, body, envelope, result and option type
  (`PartnerAccountResource`, `PartnerWithdrawalCreateResult`,
  `BalanceResource`, `AccountRequestOverrides` and so on). The methods stay
  on `KashClient`. `@kashdao/sdk/schemas` holds every Zod schema, the new
  ones included (`PartnerAccountResourceSchema`, `UsdcAtomicSchema`,
  `WithdrawalFailedStatusSchema` and so on). The partner webhook payload
  types and schemas are also on `@kashdao/sdk/webhooks`.
- **Value sets the API may grow are open.** The partner webhook
  `reason`, destination `network`, withdrawal `errorCode` and
  `withdrawal.failed` `status`, and the new account and withdrawal
  `status` fields, accept a value this SDK version does not know and keep
  it, instead of `constructEvent` or the read throwing. Their types are the
  known values plus `string`, so the known ones still autocomplete; give a
  `switch` on them a `default`. The envelope, `type`, ids, amounts and
  timestamps stay strict.
- `@kashdao/sdk/testing`: the mock client has `balance` and
  `partnerAccounts` (with `withdrawals`) and the fixtures
  `DEFAULT_PARTNER_ACCOUNT`, `DEFAULT_PARTNER_WITHDRAWAL`,
  `DEFAULT_PARTNER_WITHDRAWAL_QUOTE` and `DEFAULT_BALANCE`.
  `MockKashClient` is now picked from the real client classes, so every
  method takes exactly the real parameters (options and `account`
  included), and the mock applies the real client's checks (UUID ids and
  `account`, idempotency-key format, list limits). Override handlers
  receive the call's options.
- `generateTestWebhookSignature({ payload, secret, timestampMs? })` in
  `@kashdao/sdk/testing` returns the `X-Kash-Signature` value Kash would
  send, for unit-testing a webhook receiver.
- **Withdrawal fee disclosure.** `PartnerWithdrawalQuote` gains
  `networkFeeAtomic` (the most the network fee will cost, including
  creating the destination's USDC account on a first withdrawal to it),
  `networkFeeEstimated` and `totalDebitAtomic` (what leaves the balance:
  amount plus fee when charged on top, the amount on a send-all);
  `PartnerWithdrawalResource` gains `networkFeeAtomic` (the fee charged,
  `null` until charged). All four are optional, in the types and at
  runtime: an API release without fee disclosure omits them, so treat an
  absent value as "not disclosed", never as zero.
- `effectivePrice` on quotes is documented with its unit: atomic USDC per
  WAD token unit, so 0.42 USDC per token reads as about `4.2e-13`. The
  testing fixtures `DEFAULT_QUOTE_BUY` and `DEFAULT_QUOTE_SELL` now carry
  values in that unit (they held 0.421 and 0.42, which the API never
  produces).
- README: a units section. `trades.create` takes `amount` as a USDC decimal
  string; balances, withdrawals, quotes and webhooks use atomic units.
- `markets.list()` takes `category`, `subcategory` and `chain` (`solana` or
  `evm`), and `MarketResource` declares the `category`, `subcategory` and
  `chain` the API serves from version 2026-08-19.
- **Partner webhooks.** `WebhookEventSchema` and `webhooks.constructEvent`
  parse the eight account, withdrawal and payout events a partner
  organisation receives: `account.active`, `account.provisioning_failed`,
  `account.destination_changed`, `account.released`, `withdrawal.submitted`,
  `withdrawal.completed`, `withdrawal.failed` and `payout.completed`. Until
  now each of these verified and then threw `KashValidationError`. Their
  payload schemas and types are exported from the new `@kashdao/sdk/webhooks`
  subpath (`AccountActivePayloadSchema`, `WithdrawalFailedPayload` and so on),
  with `PartnerDestinationSchema`, `PartnerDestinationNetworkSchema`,
  `PartnerAccountFailureReasonSchema` and `WithdrawalFailureCodeSchema`. The
  root entry does not re-export them. Partner timestamps accept a UTC offset
  as well as `Z`, as the server does. A withdrawal payload's
  `deliveredAmountAtomic` is what was measured to arrive, `null` until then,
  on a failed or cancelled withdrawal and always to Arc, where
  `minimumDeliveredAtomic` is the least the bridge quote guarantees.
- `TradeRejectedPayloadSchema` and `TradeRejectedPayload` are exported from
  `@kashdao/sdk/webhooks`. The `trade.rejected` event already parsed; its
  payload type was not reachable.

### Changed

- **Breaking: the SDK now depends on zod 4** (`zod ^4.6.6`, was
  `^3.25.76`). Every zod below 4.6.6 is affected by GHSA-mrhx-c7xc-m3w5
  (high: memory exhaustion while validating oversized constrained
  collections), and the SDK validates every response it receives. What a
  partner sees change:
  - **Exported schemas are zod 4 schemas** (`TradeResourceSchema`,
    `WebhookEventSchema`, the partner schemas and the rest). Composing them
    into a schema built with a zod 3 `z` (`z.object({ trade:
TradeResourceSchema })`), or passing them to a zod 3 tool such as
    `zod-to-json-schema`, no longer works. Migration: depend on
    `zod@^4.6.6` yourself so your package manager installs one copy, build
    around the schemas with that `z`, and use zod 4's `z.toJSONSchema` for
    JSON Schema.
  - **Schema API details:** a refined body (`UpdatePartnerAccountBodySchema`)
    is a `ZodObject` (read `.shape` directly; zod 3's `.innerType()` is
    gone); `MetaSchema` is a loose object (`z.looseObject`). Ids are still
    accepted in the same 8-4-4-4-12 hex form as before.
  - **Validation issues read differently.** `KashValidationError.issues`
    and `KashConfigurationError.issues` carry zod 4's issue codes and
    messages: a bad format is `invalid_format` (was `invalid_string`), a
    value outside a closed set is `invalid_value` (was
    `invalid_enum_value`), and messages read like `Invalid input: expected
number, received string`. Paths are unchanged (`issues[].path` is still
    a dot-joined string on validation errors and an array of strings and
    numbers on configuration errors). Branch on `err.code`
    (`VALIDATION_FAILED`, `SDK_VALIDATION`) and `issues[].path`, not on the
    issue message.
  - **Bundle size.** The SDK's own code is unchanged in size (13.8 kB
    brotli, zod excluded), but zod 4's classic API does not tree-shake as
    zod 3's did: bundled with its zod, the main entry measured 26.3 kB
    brotli on zod 3 and 88.6 kB on zod 4. Server-side Node users are
    unaffected; browser and edge bundles grow accordingly.
- **The `@kashdao/sdk/webhooks` bundle budget rose from 2 kB to 5 kB.** The
  entry now loads the shared schema entry, `@kashdao/sdk/schemas`, so both
  hand out the same schema objects; it measures 3.56 kB brotli, zod excluded.
- **Breaking: every response and webhook value set is open**, not only the
  new partner ones: `TradeStatus`, the trade, prediction, trace and
  trade-webhook `side`, `MarketStatus` (market and quote),
  `MarketResolutionState`, `MarketNotTradeableReason`, `MarketChainFamily`,
  `resolution.settlementStatus`, `RedemptionKind`, the `webhookDelivery` and
  webhook event `status`, and the health `status`. A value the API adds
  parses and is kept, and a trade in an unknown status is never terminal for
  `waitForCompletion` and matches no type guard. This breaks in two ways:
  - **Types:** each type is the known members plus `string`. Assigning one
    to a closed union (for example a trade's `side` to `TradeSide`), or an
    exhaustive `switch` with no `default`, no longer compiles.
  - **Runtime:** `TradeStatusSchema`, `MarketStatusSchema`,
    `MarketResolutionStateSchema`, `MarketNotTradeableReasonSchema` and
    `RedemptionKindSchema`, exported as Zod enums in 0.3.x, are now open
    string schemas. They keep `.options` (the known values, in the same
    order), but lose `.enum`, `.Enum`, `.Values`, `.extract()` and
    `.exclude()`, so `TradeStatusSchema.enum.completed` throws a
    `TypeError` in JavaScript; and their `.parse()` / `.safeParse()` now
    accept any non-empty string, so code that validated its own stored
    values with them no longer rejects an unknown one.
  - **Migration:** compare with the string literal (`status === 'completed'`)
    or read the known list from `.options`; for strict validation build a
    closed enum from it, `z.enum(TradeStatusSchema.options)`, which accepts
    exactly the values this SDK version knows.

  Request values stay closed (`TradeSideSchema`, `QuoteActionSchema`, the
  `markets.list` filters), as do a quote's `action` and `units`, webhook
  `type` literals and each webhook's per-type `status`.

- `kash.traces.get()` no longer fails when the API adds a field to a trace
  event or to `retention`: `TraceEventDataSchema` and `TraceRetentionSchema`
  strip unknown fields like every other response schema.
- **Breaking for a caller who set `Kash-Account` through `headers`:** it is
  now an SDK-managed header, dropped from the client-level and per-call
  `headers` and set only through the `account` option. A client-level
  value reached routes that refuse it, so pass `account` on each call
  instead.
- `WebhookEventType` and `WebhookEvent` gain the eight partner members. A
  `switch (event.type)` with an exhaustiveness check (`assertNever`) on the
  four trade types no longer compiles: add the partner cases, or a
  `default` branch if your key receives no partner webhooks.

### Fixed

- `trades.waitForCompletion` on a trade still `pending_confirmation` says
  what to do (confirm it with `trades.confirm`, then wait). Its code stays
  `TRADE_NOT_AWAITING_CONFIRMATION`, as published, though the trade IS
  awaiting confirmation; the JSDoc and README explain the name.
- A caller header spelled `x-kash-api-version` (any casing other than the
  SDK's own `X-Kash-Api-Version`) was sent alongside the SDK's API version
  pin rather than dropped: the reserved-header list named `kash-version`, a
  header the SDK never sends.
- A high-value trade whose first `202` was lost no longer comes back from
  `trades.create` without its `confirmation`. The API does not store the
  token for an `Idempotency-Key` replay, so when the SDK's retry gets a
  held trade (`pending_confirmation`) with no token, it sends the call once
  more with the same `clientRequestId` and a fresh key, and the API answers
  with a new token (the earlier one stops working). One extra request at
  most; nothing is placed twice.

## [0.3.0] — 2026-10-20

### Added

- **`CreateTradeBody.ambassadorToken`** (optional): the Market Ambassadors
  share-link token, which the API uses to attribute the trade for
  revenue-share settlement. 1-128 characters of `[A-Za-z0-9_-]`, matching the
  API's own schema; an unknown or expired token leaves the trade unattributed
  rather than failing it. `AmbassadorTokenSchema` and `AmbassadorToken` are
  exported.

- **`MarketResource.tradeable` and `MarketResource.notTradeableReason`**, also
  on the quote's `QuoteMarketSummary`. `tradeable` says whether the API would
  accept a trade on the market right now, by the same rule that refuses one
  with `409 MARKET_NOT_TRADEABLE`; `notTradeableReason` is `null` when it is
  true, else `'resolved' | 'cancelled' | 'inactive' | 'frozen'`
  (`MarketNotTradeableReasonSchema`, `MarketNotTradeableReason`, exported).
  Use them instead of `status === 'ACTIVE'`: a market cancelled on chain or
  past its freeze deadline keeps `status: 'ACTIVE'`. Both are optional in the
  schema, so a response from an API deployment that predates them still
  parses; absent means "not stated", not "tradeable".
- **Conditional GETs, on by default.** The client remembers each GET
  response's `ETag` and sends it back as `If-None-Match`; a `304 Not Modified`
  resolves to the remembered value, re-validated against the schema and
  returned as a fresh object. No code change is needed to benefit. New config:
  `conditionalRequests` (default `true`) and `conditionalCacheMaxEntries`
  (default `256`, LRU). The `onResponse` hook gains `notModified`, and reports
  `status: 304` for a revalidated call. `If-None-Match` is now an SDK-managed
  header: a caller-supplied value is dropped, as for `Idempotency-Key`.
- **`portfolio.watchPositions(params?)`**: an async iterator that yields the
  positions once, then only when they change, backing off from
  `minIntervalMs` (5 s) to `maxIntervalMs` (60 s) while they do not.
  `WATCH_POSITIONS_DEFAULTS` and `WatchPositionsParams` are exported.
- `TraceResource.retention` (`TraceRetentionSchema`, `TraceRetention`):
  `{ windowDays, expired }`. The API now deletes trace events once they are
  90 to ~121 days old; `expired: true` means the trade predates the window, so
  an empty or short `events` array means the events are no longer retained.
  Optional in the schema so a response from an API deployment that predates
  the field still parses.

### Changed

- A `304` the SDK did not ask for now throws `KashValidationError` with code
  `SDK_UNEXPECTED_NOT_MODIFIED`. It previously surfaced as an unclassified
  HTTP error.

### Upgrading

- Clients that poll `portfolio.positions()` should upgrade: an unchanged poll
  becomes a body-less `304` that the API answers without running the
  positions query. Moving the loop to `watchPositions` also cuts the request
  count while nothing changes.

### Documentation

- The README and doc comments say the API's default version (used when no
  `X-Kash-Api-Version` is sent) is `2026-08-19`, the version this SDK pins;
  they previously named `2026-04-29`. No behaviour change: the SDK always
  sends `SDK_API_VERSION` unless `apiVersion` overrides it.
- Solana is the example chain throughout the README, the doc comments and the
  examples. Base (EVM) is sunset: no Base market is open. `chainRef` values
  such as `evm:8453` still parse, because historical Base trades and markets
  are still returned.
- `TradeResource.txHash` now carries the base58 signature of a `completed`
  Solana trade on API version `2026-08-19`, which this SDK pins. The API
  previously sent `null` there. The schema already accepted base58, so no
  code changes. On `2026-04-29` a Solana trade still reads `null`.

## [0.1.5] - 2026-10-01

Solana-cutover hotfix. `SDK_API_VERSION` is unchanged (`2026-04-29`), so a
`^0.1.3` consumer picks this up with no code change. **Exported types are
unchanged for every field below except one** — `PredictionResource.logIndex`,
called out under _Changed_ because keeping it strict would make this release
reject real responses on the pinned version.

0.1.4 was prepared in the monorepo but never published to npm. Everything it
contained ships here, so this entry lists all of it.

### Fixed

- **A Solana `trade.completed` webhook no longer throws in your handler.**
  `TradeCompletedPayload.txHash` accepted only an EVM hash (`0x` + 64 hex) in
  0.1.3, so `WebhookEventSchema.parse` and `webhooks.constructEvent` rejected
  every Solana delivery, whose transaction id is a base58 signature. It now
  accepts either form. `TradeResource.txHash` accepts the same two forms.
  (The type is `string` either way.)
- **An unkeyed `POST` can no longer be duplicated by a retry.** In 0.1.3 a
  `trades.create()` without an `Idempotency-Key` or `clientRequestId` was
  retried up to `maxRetries` times on a transport error, and a reset after the
  server had accepted it placed a second real trade. Every `POST` without a
  caller-supplied key now gets one generated by the SDK, once per call and
  shared by all its retry attempts (`crypto.randomUUID()`, falling back to
  `crypto.getRandomValues()`). A key you pass always wins; `GET`s are
  unaffected. **When the runtime has no `crypto` source at all, that `POST` is
  sent once and not retried** (`maxRetries` is treated as 0 for it) rather than
  repeating an unprotected write. If you relied on retries in such a runtime,
  pass your own `idempotencyKey`.

### Added

- `chainRef` on the trade resource (`trades.create/get/list/confirm`), on every
  trade webhook payload, on `MarketResource` and on `QuoteMarketSummary` —
  `"evm:8453"`, `"solana:mainnet-beta"`. Optional everywhere. Webhooks carry it
  on every delivery whatever version your key pins; the resources carry it from
  API version `2026-08-19`.
- `MarketResource.resolution` — the dispute-window settlement state
  (`proposedOutcomeIndex`, `proposedAt`, `finalizableAt`, `settlementStatus`,
  `disputeOpen`), or `null` when the market has no pending proposal. Optional:
  an API deployment that predates it omits the key.
- `MarketResource.resolutionState` — the market's coarse resolution state
  (`resolving`, `proposed`, `settling`, `resolved`, `cancelled`), or `null`
  before expiry. It never says who is resolving the market. Optional. Its enum
  is exported as `MarketResolutionStateSchema` / `MarketResolutionState`.

### Changed

- **`PredictionResource.logIndex` is `number | null`** (was `number`). A log
  index is an EVM concept; for a Solana trade the API sends `null`. The
  predictions endpoint is not version-gated, so `markets.predictions()` on a
  Solana market returns these rows on `2026-04-29` too — and 0.1.3 throws
  `Response schema mismatch: data.0.logIndex: Expected number, received null`
  on them. Keeping the old type would keep that crash, so this is the one type
  change in a patch release. Handle `null` where you read `logIndex`.
- Runtime guard: `chainId` on markets, quotes and trace events now refuses
  internal chain identifiers that are not real EVM chain ids. The API no longer
  emits them on any version. The type is unchanged.

### Unchanged on purpose

- `MarketResource.chainId` and `QuoteMarketSummary.chainId` stay **required
  `number`**, as in 0.1.3. The pinned `2026-04-29` never serves a non-EVM market
  or quote (`/v1/markets` filters them out; `/v1/markets/{id}` and the quote
  endpoints answer `400 CHAIN_NOT_SUPPORTED`), so every response it sends
  carries one. Passing `apiVersion: '2026-08-19'` to a 0.1.x client makes Solana
  markets fail to parse; upgrade to 0.2.0 for that version.

### Documentation

- `PortfolioSummary.smartAccountAddress` may be a **base58 Solana wallet
  address**, not a `0x` smart account, for a user whose funds live on Solana.
- `TradeResource.txHash` is **`null` for every Solana trade**, on every API
  version, even once `completed`. Read the signature from the
  `trade.completed` webhook instead.

## [0.1.0] — 2026-05-20

Initial public release.

### Added

- **Resources** — fluent client for every public API surface:
  - `kash.markets` — `list()`, `get(id)`
  - `kash.quotes` — `buy(...)`, `sell(...)` (price simulation, no funds moved)
  - `kash.trades` — `create(...)`, `confirm(id, { token })`, `get(id)`,
    `waitForCompletion(id)`, `list(...)`
  - `kash.portfolio` — `get()`, `positions()`
  - `kash.account` — `usage()`
  - `kash.webhooks` — `list(...)`, `redeliver(eventId)`, `rotateSecret()`,
    `verifySignature(...)`
  - `kash.traces` — `get(correlationId)` for end-to-end request tracing
  - `kash.healthCheck()` — non-throwing API liveness probe
- **Auto-routing** — a `kash_test_*` API key targets staging
  (`api-staging.kash.bot`); a `kash_live_*` key targets production
  (`api.kash.bot`). Explicit `baseUrl` or `KASH_BASE_URL` always wins.
- **Typed errors** — `KashAuthenticationError`, `KashValidationError`,
  `KashRateLimitError`, `KashServerError`, `KashNetworkError`,
  `KashTimeoutError`, `KashAbortedError`, `KashConflictError`,
  `KashNotFoundError`, `KashConfigurationError`. Each carries `code`,
  `statusCode`, `requestId` where available; `KashError` is the common
  base for `instanceof` checks.
- **Production-grade retries** — exponential backoff with jitter on
  429 / 5xx / network / timeout. Honors server-supplied `Retry-After`
  with a configurable cap. Tunable via `maxRetries`,
  `retryBaseDelayMs`, `retryMaxDelayMs`, `maxRetryAfterMs`.
- **Idempotency** — pass `idempotencyKey` to `trades.create()` to make
  it safe to retry. Replays return the cached response.
- **Observability hooks** — `onRequest`, `onResponse`, `onRetry`,
  `onError` for tracing / metrics. No mutation; logging only.
- **Webhook signature verification** — `kash.webhooks.verifySignature(...)`
  reconstructs the Stripe-style `t=<ms>,v1=<hex-hmac>` header against
  the raw body using the customer's webhook secret. Tolerates multiple
  `v1=` entries (7-day rotation overlap window).
- **`@kashdao/sdk/testing`** — mock client + builders for integration
  tests; no real HTTP calls.
- **`Page<T>`** iterator — webhooks and trades listing returns a
  page-aware iterator with `.cursor`, `.hasMore`, and `for await`
  support.
- **Native fetch** — zero deps beyond Zod. Works in Node 22+, Bun,
  Deno, Cloudflare Workers, Vercel Edge.
- **Full TypeScript types + JSDoc** on every public symbol; `tsdoc`
  comments render in IDEs.

### Server-side behavior (no SDK code changes; documented for awareness)

- The public API now returns `503 RATE_LIMIT_UNAVAILABLE` when the
  rate-limit service is momentarily unreachable
  AND the per-task circuit breaker is still closed. SDK consumers
  see this as a regular `KashServerError` with `err.code ===
'RATE_LIMIT_UNAVAILABLE'`, `err.statusCode === 503`, and
  `err.retryAfterSeconds === 1`. The default retry policy
  (`maxRetries: 3`, honours `Retry-After`) auto-retries these so
  most transient blips are invisible to application code.
  Distinct from `RATE_LIMIT_EXCEEDED` (429, you went over your
  quota) and `DEPENDENCY_UNAVAILABLE` (503, sustained infra
  outage). Consumers building dashboards / metrics that want to
  count rate-limit-subsystem failures separately can branch on
  `err.code === 'RATE_LIMIT_UNAVAILABLE'`. See
  https://docs.kash.bot/developer-docs/api-errors/RATE_LIMIT_UNAVAILABLE
  for the full contract.
